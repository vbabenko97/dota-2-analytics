# Narrow Offline CI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a GitHub Actions workflow that checks the offline fast suite and the established miniature release contract on changes, and runs the unfiltered suite only as scheduled or manually dispatched early warning.

**Architecture:** `.github/workflows/ci.yml` is the sole new implementation file. Pull requests and pushes run Ruff plus the non-slow suite except for Plan 3's named miniature-release contract, then invoke that contract once in a separate job so its release envelope is visible in the workflow. Scheduled and manually dispatched runs execute Ruff and the unfiltered suite instead; this warning path has no release authority and never replaces the local near-lock runbook, local pre-release verification, or the repository's completion checks.

**Tech Stack:** GitHub Actions, `actions/checkout`, `actions/setup-python`, `astral-sh/setup-uv`, locked `uv` environment creation, Python 3.12, pytest, Ruff.

Plan 3 owns `tests/test_cli_release.py::test_miniature_release_is_deterministic_and_verifiable`. That test creates two isolated temporary Git repositories, each with its own registry, from an identical fixed source commit and identical input bytes. It injects deterministic fake producer outputs while exercising real release preflight result consumption, manifestless staged validation, manifest-last publication, and `verify_run_bundle` for the bundle produced in each repository. It also proves ordinary release never invokes the historical frozen oracle; Plan 3 tests the separate non-publishing frozen regression independently. This is the CI miniature-release envelope; CI must not run the expensive predictive producers or write a real repository release bundle.

## File structure

- Create: `.github/workflows/ci.yml` — all CI event routing, environment setup, and offline validation commands.
- Reuse without modification: `tests/test_cli_release.py::test_miniature_release_is_deterministic_and_verifiable` — deterministic miniature release and provenance verification introduced by Plan 3.

No static Python workflow-contract test is warranted. Parsing YAML in pytest would duplicate GitHub Actions' syntax validation without establishing that the configured actions, locked environment, or commands work on a runner. The workflow execution itself is the authoritative contract check. This plan adds or changes no test, so it adds no mutation observation; Plan 3 remains responsible for the required mutation-killing docstring and observed mutation failure of its miniature-release test.

- [ ] **Step 2: Create the GitHub Actions workflow**

Create `.github/workflows/ci.yml` with exactly this content:

```yaml
name: CI

on:
  pull_request:
  push:
  workflow_dispatch:
  schedule:
    - cron: "0 0 * * *"

permissions:
  contents: read

jobs:
  lint-and-fast-tests:
    if: github.event_name != 'schedule' && github.event_name != 'workflow_dispatch'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@de0fac2e4500dabe0009e67214ff5f5447ce83dd # v6.0.2
        with:
          persist-credentials: false
      - uses: actions/setup-python@a309ff8b426b58ec0e2a45f0f869d46889d02405 # v6.2.0
        with:
          python-version: "3.12"
      - uses: astral-sh/setup-uv@c771a70e6277c0a99b617c7a806ffedaca235ff9 # v9.0.0
        with:
          version: "0.9.12"
      - run: uv sync --locked --group dev
      - run: .venv/bin/python -m ruff check .
      - run: >-
          .venv/bin/python -m pytest -q -m "not slow"
          --deselect=tests/test_cli_release.py::test_miniature_release_is_deterministic_and_verifiable

  miniature-release-contract:
    if: github.event_name != 'schedule' && github.event_name != 'workflow_dispatch'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@de0fac2e4500dabe0009e67214ff5f5447ce83dd # v6.0.2
        with:
          persist-credentials: false
      - uses: actions/setup-python@a309ff8b426b58ec0e2a45f0f869d46889d02405 # v6.2.0
        with:
          python-version: "3.12"
      - uses: astral-sh/setup-uv@c771a70e6277c0a99b617c7a806ffedaca235ff9 # v9.0.0
        with:
          version: "0.9.12"
      - run: uv sync --locked --group dev
      - run: >-
          .venv/bin/python -m pytest -q
          tests/test_cli_release.py::test_miniature_release_is_deterministic_and_verifiable

  full-suite-early-warning:
    if: github.event_name == 'schedule' || github.event_name == 'workflow_dispatch'
    name: Full suite early warning (not release verification)
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@de0fac2e4500dabe0009e67214ff5f5447ce83dd # v6.0.2
        with:
          persist-credentials: false
      - uses: actions/setup-python@a309ff8b426b58ec0e2a45f0f869d46889d02405 # v6.2.0
        with:
          python-version: "3.12"
      - uses: astral-sh/setup-uv@c771a70e6277c0a99b617c7a806ffedaca235ff9 # v9.0.0
        with:
          version: "0.9.12"
      - run: uv sync --locked --group dev
      - run: .venv/bin/python -m ruff check .
      - run: .venv/bin/python -m pytest -q
```

The three full action SHAs and the `setup-uv` executable version `0.9.12` are explicit implementation pins registered by this plan; the `# vX.Y.Z` comment on each `uses:` line records the upstream release tag its SHA was verified against (checked via the GitHub API during plan review), so the mapping is auditable in the artifact itself. They claim no mechanical lineage from existing repository state; change them only through an explicit reviewed workflow update. `uv.lock` governs Python project dependency resolution for `uv sync --locked --group dev`; it neither selects nor attests the uv executable. The read-only workflow does not retain checkout credentials because it performs no Git operation after checkout.

The one `--deselect` is an exact handoff, not a broad provenance or release exclusion: it names only the test run once by `miniature-release-contract`. Keep it coupled to that job's nodeid if Plan 3 renames the test. The cron is an operational scheduling choice, not an empirical project result. Do not add caches, service containers, package publication, artifacts, repository writes, network fixtures, broad test exclusions, or a real `ti26.cli_release` invocation.
